# Linux Per-User XKB Variants

## Status and intent

This document is the adopted architecture for Phase 14. P14.1 project identity and immutable
derivation persistence, P14.2 neutral diffing/derived translation, P14.3 isolated bundle generation,
P14.4 capability probing/verification, P14.5 ownership-aware install planning, P14.6 transactional
installation/recovery, and P14.7's explicit application workflow are implemented. Compatibility
closure and the final end-to-end matrix remain for P14.8.

The feature is deliberately narrower than a general XKB editor or installer. A user imports a
layout already installed by the operating system, changes the mappings KeyboardStudio supports,
and publishes those changes as a new user-scoped variant of the original layout. Examples are:

- `Polish - KeyboardStudio` under the existing Polish layout;
- `Albanian - KeyboardStudio` under the existing Albanian layout;
- multiple KeyboardStudio variants under the same existing layout.

KeyboardStudio does not create a new language, replace the distribution's layout, edit
`/usr/share/X11/xkb`, or attempt to model every XKB component. In XKB terms, the result is a variant
associated with the original layout's RMLVO identity and backed by a small symbols override.

The implemented standalone symbols backend remains available and is documented in
[`LINUX-XKB.md`](LINUX-XKB.md). The implemented importer is documented in
[`LINUX-LAYOUT-IMPORT.md`](LINUX-LAYOUT-IMPORT.md). Phase 14 composes those two capabilities and adds
safe, explicit per-user installation.

---

## 1. User workflow

The supported workflow is:

1. Import a layout and optional variant from the installed system catalog, for example
   `pl(qwertz)` or `al(basic)`.
2. Edit one or more supported key mappings in KeyboardStudio.
3. Enter a stable custom variant ID and display name. The base layout and base variant are shown as
   read-only derivation information.
4. Generate a per-user XKB bundle into the normal build output. Generation does not modify the
   running system.
5. Verify the proposed bundle against the host's XKB database.
6. Explicitly choose **Install**, **Update**, **Verify installed**, or **Uninstall**.
7. Select the new variant in the desktop's keyboard settings. KeyboardStudio does not activate it.

Importing a loose symbols file remains useful for editing and standalone export, but it is not an
installable system-derived variant in the first implementation. KeyboardStudio cannot safely assume
that an arbitrary file will remain available as a system base.

An existing version-2 project that records only import provenance also remains editable and can use
standalone export. It must be re-imported before Phase 14 installation is enabled because it has no
immutable import baseline from which a safe delta can be calculated.

## 2. What is written, and what is not

The effective user XKB root is:

```text
${XDG_CONFIG_HOME:-$HOME/.config}/xkb
```

The directory does not need to exist before the first installation. KeyboardStudio creates only the
required subdirectories and files after the user explicitly approves installation.

A representative installation is:

```text
~/.config/xkb/
  symbols/
    keyboardstudio      # app-owned definitions for all installed projects
    pl                  # small bridge sections for custom Polish variants
    al                  # small bridge sections for custom Albanian variants
  rules/
    evdev.xml           # minimal registry additions for desktop discovery
```

The substantial generated definition lives in the dedicated `symbols/keyboardstudio` file. A
same-name bridge file is needed only because the standard XKB rules map the RMLVO pair
`layout=pl, variant=<name>` to section `<name>` in `symbols/pl`. The bridge contains only the
KeyboardStudio-owned section and forwards it to the dedicated file. It does not copy the
distribution's Polish definitions.

The user rules XML adds the variant to the existing system layout entry. It does not copy the whole
system registry. libxkbregistry merges the minimal user entry with the system entry by layout name.

KeyboardStudio never writes to:

```text
/usr/share/X11/xkb
/usr/share/xkeyboard-config-*
/etc/xkb
```

It also never changes GNOME, KDE, compositor, X11, or console settings and never makes the generated
layout active.

### Example generated files

The dedicated definition can look like this:

```xkb
// Generated by KeyboardStudio. Managed file; do not edit by hand.
// BEGIN KeyboardStudio 7c31d5f2a19e40a4b0ef64f01a295135
partial alphanumeric_keys
xkb_symbols "ks_7c31d5f2" {
    include "%S/pl(qwertz)"
    name[Group1] = "Polish - KeyboardStudio Programmer";

    key <AC01> { type[Group1] = "FOUR_LEVEL_SEMIALPHABETIC",
                 symbols[Group1] = [ a, A, U0105, U0104 ] };
};
// END KeyboardStudio 7c31d5f2a19e40a4b0ef64f01a295135
```

The matching bridge in `symbols/pl` can look like this:

```xkb
// BEGIN KeyboardStudio ks_7c31d5f2
partial alphanumeric_keys
xkb_symbols "keyboardstudio_programmer" {
    include "keyboardstudio(ks_7c31d5f2)"
};
// END KeyboardStudio ks_7c31d5f2
```

The registry overlay adds a variant beneath the existing Polish layout:

```xml
<layout>
  <configItem>
    <name>pl</name>
  </configItem>
  <variantList>
    <variant>
      <configItem>
        <name>keyboardstudio_programmer</name>
        <shortDescription>pl</shortDescription>
        <description>Polish - KeyboardStudio Programmer</description>
      </configItem>
    </variant>
  </variantList>
</layout>
```

`%S` means the system XKB root. It is important here: the generated definition must inherit
`pl(qwertz)` from the distribution even though a higher-priority user file named `symbols/pl`
exists. It also avoids a circular include through the user bridge.

The public variant name (`keyboardstudio_programmer`) is stable and readable. The internal section
name (`ks_7c31d5f2`) is derived from a stable project installation ID, so renaming the project does
not orphan an installed section and two projects cannot silently claim the same definition.

### Are symbols files alone sufficient?

They are sufficient to define and compile a keymap when its RMLVO name is already known. They are
not sufficient for the complete product workflow:

- `symbols/keyboardstudio` holds the actual base include and changed keys;
- `symbols/pl`, `symbols/al`, and similar bridges let the standard rules resolve the custom variant
  as a member of the existing layout;
- `rules/evdev.xml` makes that variant discoverable to libxkbregistry-based desktop settings.

The user edits mappings only in KeyboardStudio. The application generates and, after an explicit
install command, manages these XKB files. It never asks the user to hand-edit the distribution's
symbols file.

### Alternatives considered

| Option | Decision |
|---|---|
| Edit `/usr/share/X11/xkb/symbols/pl` directly | Rejected: requires elevated access and package updates overwrite it |
| Copy the complete Polish/Albanian file into the user root | Rejected: freezes and shadows distribution definitions instead of augmenting them |
| Put every generated key statement directly in the user `symbols/pl` file | Valid XKB, but rejected as the primary organization because substantial generated content would be mixed into a shared language bridge |
| Publish only a new standalone `symbols/keyboardstudio` layout | Retained as the existing standalone export, but it does not naturally remain a variant of Polish, Albanian, and similar layouts |
| Add a custom text `rules/evdev` mapping every custom pair directly to the central file | Possible, but more invasive and easier to conflict with rule ordering; thin symbol bridges reuse the standard layout/variant catch-all |
| Install a system package | Possible future distribution mechanism, but outside a per-user editor workflow |

## 3. Why updates do not overwrite the customization

Distribution package updates own the system XKB roots, not the user's XDG configuration root.
Therefore an xkeyboard-config update does not overwrite KeyboardStudio files.

The generated section contains only a system include and changed keys. This gives the desired
update behavior:

- unchanged keys continue to inherit the current distribution definition;
- KeyboardStudio-owned changes remain in the user directory;
- improvements to the system base can flow through without regenerating a complete copied layout.

This is not a promise that all future system updates are behaviorally compatible. A package update
can rename or remove the base layout/section, change key types, or alter inherited behavior. The
installation manifest therefore records the base identity and verification state. **Verify
installed** recompiles the custom variant after system updates and reports drift or failure without
editing the system files.

## 4. Runtime requirements and compatibility

The path is a libxkbcommon user-configuration feature, not a universal Linux keyboard path. Support
is decided from capabilities at runtime, never from the distribution name alone.

### Required for managed installation

- Linux running a Wayland session whose compositor compiles keymaps with libxkbcommon;
- an absolute `XDG_CONFIG_HOME`, or an available absolute home directory for the `.config` fallback;
- libxkbcommon 1.11.0 or newer for `%S` system-section includes;
- libxkbcommon 1.12.2 or newer is the recommended supported baseline because it also contains the
  canonical-root fallback needed by some xkeyboard-config 2.45+ installations;
- `xkbcli compile-keymap` for pre-install and post-install compilation checks;
- writable, non-suspicious user configuration and state paths;
- a desktop configuration tool using libxkbregistry if the variant must appear automatically in its
  layout chooser.

libxkbcommon 1.9.0 introduced correct fallback between user and system files with the same name.
KeyboardStudio nevertheless requires 1.11.0 for managed installation because the `%S` include is
the explicit, non-recursive way to inherit the system section.

### Unsupported or reduced modes

| Detected host | KeyboardStudio behavior |
|---|---|
| Wayland, supported libxkbcommon, `xkbcli`, libxkbregistry-aware desktop | Generate, verify, install, update, verify installed, and uninstall |
| Wayland and keymap compilation works, but registry discovery cannot be demonstrated | Generate and verify; installation may be offered with a warning that the desktop chooser may not list it |
| Wayland with old or unknown libxkbcommon, or no `xkbcli` | Export the bundle only; do not mutate the user XKB root |
| X11 session | Export only; the X server uses hard-coded XKB paths and does not treat the XDG directory as a general replacement root |
| Headless or unknown session | Export and isolated verification only |

The implemented capability result is a first-class value containing the detected session type,
effective configuration and state paths, parsed libxkbcommon version, `xkbcli` path/version output,
canonical system root, and registry-query support. It reports managed-installation or export-only
mode plus diagnostics; a distro label is never used as evidence that installation is safe. The UI
will present this value in P14.7.

### Ten common distributions

The same rule applies to all of these distributions. The path is expected to work for a normal
unprivileged Wayland session using a sufficiently recent libxkbcommon; it is not guaranteed merely
because the distribution appears in this table.

| Distribution | Per-user path assessment |
|---|---|
| Fedora Workstation | Expected on the default Wayland desktop; runtime probe remains authoritative |
| Ubuntu | Expected on Wayland; X11 sessions are export-only |
| Debian | Expected when the selected desktop session uses Wayland and the required library version |
| Arch Linux | Expected on a configured Wayland compositor with the required packages |
| Manjaro | Expected on Wayland; desktop and package versions must be probed |
| openSUSE Tumbleweed | Expected on Wayland with current libxkbcommon |
| openSUSE Leap | Conditional on the shipped/backported libxkbcommon version and session type |
| Linux Mint | Conditional; installations still using X11 are export-only |
| Pop!_OS | Expected when the active desktop session is Wayland and uses libxkbcommon |
| KDE neon | Expected on Plasma Wayland; registry discovery is verified separately |

The reference Fedora host inspected while this plan was written runs Plasma Wayland with
libxkbcommon 1.13.1 and xkeyboard-config 2.47, so its library side qualifies. Its absent
`~/.config/xkb` directory is normal. `xkbcli` is not installed there, so managed installation must
stay disabled until the distribution's libxkbcommon tools package is installed.

## 5. Project data and delta generation

Current import provenance says where a project came from but not what every supported mapping was at
the moment of import. That is insufficient to distinguish inherited keys from user changes.

P14.1 introduced a document-envelope `LayoutDerivation` and schema version 3. It is application
bookkeeping, not a Core keyboard-layout concept:

```text
LayoutDerivation
  projectInstallationId    stable 32-digit GUID representation
  sourceId                 linux-xkb
  sourceOrigin             system
  baseLayoutId             pl
  baseVariantId            qwertz
  resolvedBaseSectionId    qwertz
  importedAtUtc            ...
  baselineMappings         immutable representable mappings at import time
  importFidelity           exact/reduced/partial
  sourceFingerprint        optional source hash
  includeChainFingerprint  optional include-chain hash
```

Only an import-as-new-project from a system-origin catalog entry establishes an installable
derivation in the first version. Each baseline mapping records whether source behavior lost during
import makes that key unsafe to override. Loose-file imports, mapping replacement, startup
inference, and migrated version-2 documents do not gain a derivation. The baseline never changes
during editing or when the document is loaded. Re-importing deliberately creates a new baseline
and installation ID.

The implemented `KeyboardLayoutDiffer` compares the current Core mappings with the baseline without
knowing XKB. It reports additions, modifications, removals, logical-key changes, and the precise
changed layers in stable physical-key order. The implemented `XkbUserVariantTranslator` then emits
only changed keys. If any supported layer changes, translation carries that key's complete current
supported mapping through the highest relevant level, including an explicit `NoSymbol` where the
user cleared a level. This prevents a partial statement from accidentally retaining an old
inherited level.

The current importer intentionally drops dead keys, actions, groups above one, and levels above
four. If a changed key had unsupported source behavior that the baseline could not represent, the
translator blocks variant generation with a key-specific diagnostic. It does not infer that an
invisible source level should be erased. Later work can add explicit override intent or broader XKB
constructs.

The result of translation is separate from the existing standalone model:

```text
KeyboardProjectDocument + LayoutDerivation + XkbUserVariantMetadata
                              |
                              v
                    KeyboardLayoutDiffer
                              |
                              v
                    XkbUserVariantTranslator
                              |
                              v
                    XkbGeneratedUserBundle
```

`XkbUserVariantMetadata` contains the public variant ID and display description. It does not replace
`XkbLayoutMetadata`, which continues to describe standalone artifacts.

## 6. Proposed code architecture

The names below are the intended responsibilities, not a requirement to put several types in one
file. Every top-level C# type must follow the repository rule and live in its own `.cs` file.

```text
KeyboardStudio.Core/Layouts/Diffing/
  KeyboardLayoutDiffer.cs
  KeyboardLayoutDifference.cs
  KeyboardKeyDifference.cs
  KeyboardMappingChangeKind.cs
  KeyMappingSnapshot.cs

KeyboardStudio.Persistence/Documents/
  LayoutDerivation.cs
  LayoutDerivationDto.cs

KeyboardStudio.Linux/Model/
  XkbUserVariantMetadata.cs
  XkbUserVariantLayout.cs
  XkbUserVariantKeyMapping.cs
  XkbGeneratedUserBundle.cs
  XkbUserBundleFile.cs

KeyboardStudio.Linux/Translation/
  XkbUserVariantTranslator.cs
  XkbUserVariantTranslationResult.cs

KeyboardStudio.Linux/Generation/
  XkbUserVariantSymbolsGenerator.cs
  XkbLanguageBridgeGenerator.cs
  XkbRegistryEntryGenerator.cs
  XkbUserBundleGenerator.cs
  XkbUserBundleWriter.cs

KeyboardStudio.Linux/Verification/
  XkbUserBundleVerifier.cs
  XkbUserInstallCapabilityProbe.cs
  XkbUserInstallCapability.cs
  XkbUserBundleVerificationResult.cs
  XkbUserBundleVerificationCheck.cs

KeyboardStudio.Linux/Installation/
  IXkbUserInstallService.cs
  XkbUserInstallService.cs
  XkbInstallPlan.cs
  XkbInstallOperation.cs
  XkbInstallationManifest.cs
  XkbManagedBlockEditor.cs
  XkbRegistryDocumentMerger.cs
  XdgDirectoryResolver.cs
```

The dependency flow remains:

```text
App -> Core
App -> Persistence -> Core
App -> Linux -> Build + Core
```

Core owns a neutral diff. Persistence owns the versioned document representation. Linux owns XKB
generation, capability detection, verification, and installation. Avalonia ViewModels orchestrate
these services but do not parse XML, generate XKB, or write configuration directly.

Build and installation are distinct boundaries. P14.3 implements the first boundary as a pure,
deterministic multi-project generator plus an output writer:

- a normal Linux build may create a standalone symbols artifact or stage a derived user bundle at
  `<chosen-output>/xkb-user-bundle`;
- no build invocation writes to the XDG configuration root;
- installation accepts an already generated and verified bundle plus an explicit user action;
- activation remains outside both boundaries.

The bundle manifest records schema/generator versions, stable variant identities, changed physical
keys, and SHA-256 hashes of every installable file. Generation refuses internal-section and public
layout/variant collisions before producing a bundle.

P14.4 verification uses the official order-sensitive invocation shape
`xkbcli compile-keymap --include <staged-root> --include-defaults --test`. For every proposed
variant it compiles the public custom RMLVO pair, the imported base pair, and an unrelated variant
from the same system layout. When `xkbcli list`/libxkbregistry is available, it also loads the staged
root before the canonical system root and confirms the public pair appears in the merged registry.
Every check retains its arguments, output, exit code, and diagnostic instead of collapsing failure
to a boolean.

## 7. Ownership, merge, and transaction rules

KeyboardStudio shares the user XKB root with the user and other tools. Existing files are user data,
not disposable build output. P14.5 implements this section as pure merge and planning components;
P14.6 executes the resulting typed operations transactionally.

### File ownership

- `symbols/keyboardstudio` is app-owned only when it has the KeyboardStudio generated header and a
  matching installation manifest. Otherwise installation refuses to replace it.
- `symbols/<base-layout>` is shared. KeyboardStudio edits only stable comment-delimited managed
  blocks and preserves all other bytes.
- `rules/evdev.xml` is shared. It is changed through an XML-aware merger with external entity
  resolution disabled. Unknown elements and unrelated entries are preserved.
- a public `(base layout ID, variant ID)` collision is an error unless the existing entry belongs to
  the same project installation ID.
- unexpected edits to a previously managed block are conflicts, not permission to overwrite.

`XkbManagedBlockEditor` preserves all bytes outside the selected comment-delimited block and hashes
the normalized owned block. `XkbRegistryDocumentMerger` parses with DTD processing ignored and no
XML resolver, preserves unknown elements and unrelated variants, and owns entries through adjacent
project-ID comments. Both refuse missing, duplicated, malformed, unowned, or hash-mismatched target
content.

### Host-local state

Installation state does not belong in `.kbdproj`, because the project can be copied between hosts.
It is stored beneath:

```text
${XDG_STATE_HOME:-$HOME/.local/state}/keyboardstudio/xkb/
  installations.json
  backups/<transaction-id>/...
  journal.json
```

The version-1 manifest model records stable project installation IDs, installed variants, base
identities, managed file paths, whole-file and owned-content hashes, creation ownership, tool
version, and verification time. Its JSON serializer rejects invalid IDs, unsafe relative paths,
duplicate identities, unknown schemas, and malformed hashes. Backup locations and the active journal
are added by the P14.6 transaction layer rather than to each durable installation entry.

`XkbInstallPlanner` consumes only generated bundle content, an XDG path result, the manifest, and
immutable live-file snapshots. It returns exact create/replace/delete operations plus the next
manifest. It does not touch the filesystem. The planner rejects an unowned or whole-file-modified
`symbols/keyboardstudio`, changed target blocks/registry entries, public collisions, unsafe paths,
and snapshots marked as symlinks. Unrelated bridge bytes and XML nodes are retained.

### Installation transaction

Install and update use the same plan:

1. resolve XDG paths and probe host capabilities;
2. reject relative paths, unsafe ownership/permissions, unexpected symlinks, and identifier
   collisions;
3. read the current destination files and installation manifest;
4. construct the exact merged result in an isolated temporary XKB root;
5. run managed structural validation;
6. compile the custom RMLVO pair with the staged root before system defaults;
7. compile the original base and at least one unrelated variant of the same layout through that
   staged root, proving the bridge did not hide system sections;
8. verify that the staged registry exposes the custom variant when libxkbregistry tooling is
   available;
9. create recoverable backups and write a transaction journal;
10. replace destination files atomically one file at a time using same-directory temporary files;
11. compile and inspect the installed result again;
12. write the installation manifest and clear the journal;
13. on any failure, restore every affected file from the transaction backups.

Because several files are involved, the filesystem cannot make the whole operation atomic in one
rename. The journal and backups provide crash recovery and rollback across the sequence.

`IXkbUserInstallService` is the live-mutation boundary. `XkbUserInstallService` copies the complete
current user XKB tree into an isolated transaction root, applies the P14.5 plan there, and invokes
the P14.4 verifier without requiring a build-only bundle manifest. Only a successful proposed-root
verification permits live writes. It rejects export-only capability results, changed XDG roots,
group/other-writable managed directories, and symbolic links anywhere it would traverse.

Before the first live change, the service copies every affected file and the previous manifest to a
transaction-specific backup and atomically writes `journal.json`. Destination content is rehashed
immediately before mutation. Creates and replacements use flushed same-directory temporary files
and atomic renames; deletes use a same-directory tombstone rename. The live root is rehashed and
verified before the new manifest is atomically installed. The journal is the commit boundary and is
removed only after all of those checks pass.

Cancellation or any ordinary I/O, validation, or verification failure after journaling restores all
destinations and the previous manifest. A journal left by process interruption is replayed
idempotently before the next install, update, verify-installed, or uninstall command. Backup hashes
are checked before recovery, and a failed recovery retains the journal and backups instead of
guessing.

Uninstall removes only sections, managed blocks, and XML nodes owned by the selected installation
ID. It deletes a shared file only when no non-KeyboardStudio content remains. After uninstall, it
again compiles the base and an unrelated variant through the proposed and installed roots, and
leaves the backup available until the transaction completes. Install, update, uninstall, and
verify-installed never activate a layout or write desktop/session settings.

## 8. UI contract

The Linux user-variant panel shows:

- source: system layout and variant, read-only;
- source fidelity and any changed-key restrictions;
- custom variant ID, validated as an XKB identifier and checked for collision;
- display name, initially `<system description> - KeyboardStudio`;
- effective user XKB and state directories;
- host capability and desktop-discovery status;
- project status: not installed, installed, update available, externally modified, broken, or base
  unavailable;
- actions: Generate bundle, Install, Update, Verify installed, Uninstall, and Open output folder.

Install, update, and uninstall always require an explicit action and show the exact paths to be
changed. A successful operation tells the user that the desktop settings may need to be reopened or
the session restarted. KeyboardStudio does not silently select the variant.

The implemented `LinuxUserVariantViewModel` and main-window card expose this contract only when the
open project has an immutable system-import derivation. The public ID defaults to
`keyboardstudio_<base-variant>` and the display name to `<source description> - KeyboardStudio`.
Both are stored as hidden Linux target-profile settings, so user edits survive save/reopen without
changing the standalone Linux build profile or the version-3 document schema. Once installed, the
public ID is read-only because it is the stable desktop-visible identity; the display name and key
mappings can still produce an update.

`LinuxUserVariantWorkflowService` performs translation/generation planning and asynchronous host
inspection behind the ViewModel. It distinguishes unavailable, export-only, not installed,
installed, update available, externally modified, broken, and base unavailable states. The card
presents import fidelity, effective XDG paths, session/tool/version/registry capability, and
structured warnings. Loose-file imports and migrated projects without a baseline receive re-import
guidance instead of an enabled installer.

Generate writes only beneath the selected build output and can be used in export-only mode. Every
live action opens a confirmation dialog listing the three possible user-XKB files plus the manifest,
journal, backup, and proposed-root transaction paths. Install, update, verify-installed, and
uninstall call the P14.6 service and refresh status afterward. Cancellation is forwarded into the
transaction and reports that any live changes were rolled back. Success explains that desktop
settings may need to be reopened or the session restarted; activation remains out of scope.

## 9. Test strategy and acceptance scenario

### Unit and golden tests

- neutral mapping diffs, including full-key emission when one layer changes;
- derivation DTO migration and old-document compatibility;
- identifier sanitization and collision rules;
- central symbols, bridge, and minimal registry golden files;
- managed-block preservation and conflict detection;
- XML merge with DTD resolution disabled, comments, unknown nodes, and pre-existing user variants;
- XDG resolution, missing directories, unsafe paths, and symlink rejection;
- manifest ownership, update, uninstall, rollback, and journal recovery.

### Linux integration tests

- stage against pinned XKB fixtures and compile with `xkbcli`;
- compile the custom variant, its base, and an unrelated same-layout variant;
- verify registry merging where libxkbregistry tooling is present;
- exercise install/update/uninstall inside temporary XDG configuration and state roots;
- assert that no test can address `/usr/share`, `/etc/xkb`, or the developer's real XDG directories.

### End-to-end acceptance scenario

1. Import `pl(qwertz)` from the system catalog as a new project.
2. Change one supported key and save/reopen the project.
3. Generate `keyboardstudio_programmer`; the derived definition contains exactly one complete key
   override and a `%S/pl(qwertz)` include.
4. On a qualifying Wayland host, install into a previously absent temporary user XKB root.
5. The registry lists the new variant beneath Polish.
6. The custom variant, `pl(qwertz)`, and another Polish variant all compile through the installed
   root.
7. Update the project and installation, then verify the new hashes.
8. Uninstall it.
9. Every unrelated byte that existed before installation is unchanged, and no system XKB file was
   written.

## 10. Deliberate exclusions

Phase 14 does not include:

- X11 installation or activation;
- system-wide installation or distribution packages;
- changing the active desktop layout;
- creating new languages or replacing XKB rulesets;
- arbitrary keycodes, types, compatibility maps, geometry, actions, macros, or groups;
- installing a derivation from a loose file or from an old project without a baseline;
- automatically rewriting a derivation when the distribution changes its base layout.

These exclusions keep the feature aligned with KeyboardStudio's purpose: partial augmentation of an
existing layout, not creation or administration of an entire XKB database.
